# Demo — what actually breaks

A post-quantum certificate is not a new kind of certificate. It is the same
X.509 you already parse, with one field grown by an order of magnitude. Nothing
rejects it because it is post-quantum; things reject it because it is *large*,
and they reject it in places that have nothing to do with cryptography.

This directory generates real fixtures and runs small probes against real
runtimes to find those places. Every number below was measured by running
these scripts, not estimated.

```bash
make build && make engine     # once
docs/demo/run.sh
```

Runtimes that are not installed are skipped loudly. A probe that exits
non-zero has found a broken default — that is the demo working.

## What the probes found

Every number below comes from a run of these scripts. The Node rows were
measured on macOS arm64 (Node 25.6.0 / OpenSSL 3.5.5) and reproduced on
ubuntu-latest (Node 22.23.2 / OpenSSL 3.5.7); the Java and PostgreSQL rows come
from [`demo.yml`](../../.github/workflows/demo.yml), which runs the whole set
on a runner that has every runtime, fails if any probe was skipped, and uploads
the transcript. Fixtures were generated by `pqc-fixtures` built from `main`
against the pinned OpenSSL 3.5.8 engine.

### Node — the certificate arrives in a request header

The pattern is ordinary mTLS: a proxy terminates TLS and forwards the verified
client certificate to the app in a header. nginx calls it
`ssl_client_escaped_cert`, AWS ALB `x-amzn-mtls-clientcert`, Envoy
`x-forwarded-client-cert`. Node's default header budget —
`http.maxHeaderSize` — is **16,384 bytes for all headers combined**.

| Certificate | PEM | URL-escaped | Result |
|---|---:|---:|---|
| RSA-2048 leaf (baseline) | 1,070 B | 1,152 B | delivered |
| ML-DSA-65 leaf | 7,753 B | 8,461 B | delivered |
| **ML-DSA-65 chain** | 23,088 B | 25,200 B | **`HPE_HEADER_OVERFLOW`** |
| **SLH-DSA-SHA2-256f leaf** | 68,248 B | 74,474 B | **`HPE_HEADER_OVERFLOW`** |

The second row is the one worth sitting with. A *single* ML-DSA-65 certificate
still fits. The three-certificate chain — what a proxy forwards when it
forwards a chain at all — does not, at 1.5× the budget. This is the mainstream
post-quantum choice, not the pathological one.

The failure mode is worse than the failure. Node's HTTP parser aborts the
message rather than answering `431 Request Header Fields Too Large`: the
server logs `HPE_HEADER_OVERFLOW` and the client sees a bare `ECONNRESET`. The
caller gets a reset connection with no status code, no body, and nothing
naming the certificate.

### Node — terminating TLS with the certificate

| Chain | Result |
|---|---|
| ML-DSA-65 | handshake completed, chain verified, `TLS_AES_256_GCM_SHA384` |
| SLH-DSA-SHA2-256f | **`ERR_SSL_UNKNOWN_CERTIFICATE_TYPE`** |

"Does your runtime support post-quantum certificates" is not one question.
Node 25.6.0 links OpenSSL 3.5.5, handles ML-DSA end to end — and refuses to
*load* an SLH-DSA certificate. The error arrives from
`tls.createSecureContext`, before `listen()`, before a client exists: the
server cannot start, and the message says nothing about size or about SLH-DSA.

### Java — the chain has to fit in one handshake message

The TLS 1.3 Certificate message carries the whole chain, and
`jdk.tls.maxHandshakeMessageSize` caps it at **32,768 bytes** by default — one
budget every certificate in the chain shares. A second default caps the
*count*: JDK 22 split it in two
([JDK-8313236](https://bugs.openjdk.org/browse/JDK-8313236)), and
`jdk.tls.server.maxInboundCertificateChainLength` defaults to **8** — the
tighter of the pair, and the one an mTLS server applies to connecting clients.

Measured on Temurin JDK 21:

| Chain | Certificates | Handshake message | vs 32,768 B | vs 8 certs |
|---|---:|---:|---|---|
| ML-DSA-65 (3) | 3 | 16,947 B | fits, 52% | fits |
| **worst-case-tls** | 3 | 150,930 B | **461%** | fits |
| **deep-chain** | 10 | 76,133 B | **232%** | **exceeded** |

`deep-chain` is the interesting row: it breaks *both* limits at once, and its
certificates are individually unremarkable. Ten ML-DSA certificates is not a
strange chain — it is a chain with a few more intermediates than usual.

Worth noting what did *not* break: JDK 21 parsed every chain, SLH-DSA
included. Java's problem here is arithmetic, not algorithm support.

### PostgreSQL — the certificate has to fit in the column, and in the index

Measured against PostgreSQL 17 with an ML-DSA-65 chain of 23,087 bytes:

| Statement | Result |
|---|---|
| `INSERT` into `varchar(4096)` | **`value too long for type character varying(4096)`** — 18,991 B over |
| `INSERT` into `text` | accepted |
| `CREATE INDEX` on the `text` column | **`index row requires 23104 bytes, maximum size is 8191`** |
| `CREATE INDEX` on `digest(pem, 'sha256')` | accepted — this is the fix |

`varchar(4096)` is nobody's considered decision; it is the number someone
picked years ago when every certificate they had was 1 KB. The index row limit
is the sharper one, because indexing a certificate column is a reasonable
thing to have done and it silently stops being possible.

## Why the fixtures come from `pqc-fixtures`

Every probe needs certificates that are the *right size*, verifiable, and
obviously not real. The fixture sets here are generated with `--preset
worst-case-tls`, `--preset deep-chain`, and a plain `--algo ml-dsa-65 --chain
3`, so their sizes come
from the FIPS 203/204/205 envelopes in `src/profile` rather than from whatever
a hand-rolled test certificate happened to produce. They carry `TEST ONLY`
subjects, 30-day validity, and `INSECURE-TEST-` filenames, and they verify
against their own root and nothing else.

The RSA-2048 baseline is generated by the same pinned engine on the same run,
so the comparison differs in the algorithm and nothing else.

## Adding a probe

A probe is any program that takes a fixture path, exercises one default, and
exits 0 if that default survived. Keep it dependency-free, make it print what
it measured before it prints its verdict, and add it to `run.sh` behind a check
for whether its runtime exists.
